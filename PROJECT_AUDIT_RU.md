Capital Live — аудит и задание для независимой проверки GPT

Срез: 6 ноября 2026 года. Все отметки времени котировок ниже указаны в UTC.
Публичный сайт: https://capitalive.vercel.app
Production deployment: dpl_Dr9kN1L7c2EgPUW8cyRWzq1C3fpA.
Проверяется фактическое окружение Capital.com DEMO. Название Capital Live не означает, что настроен LIVE-счёт.

**1. Главный вывод**

Публичный API котировок, MN1 и исторического запроса работает. Постоянное хранение полученных котировок в PostgreSQL подключено и проверено на реальном тике. Однако проект пока НЕ обеспечивает непрерывный архив 24/7 и НЕ гарантирует восстановление точной цены на момент любого произвольного EDGE.

Непрерывный worker подготовлен, но не развёрнут: в текущей диагностике `worker: null`. Получение и сохранение тиков сейчас происходит во время запросов к API. В production отсутствует `EDGE_INGEST_TOKEN`, поэтому защищённый приём EDGE ещё не активирован. Автоматического чтения новых сообщений ChatGPT нет.

Этот документ — проверяемое описание состояния, а не независимая сертификация. Проверяющий GPT должен перепроверить утверждения, сохранить ответы и явно разделить подтверждённое, ошибочное и недоступное для проверки.

**3. Архитектура и область проверки**

Next.js App Router + TypeScript, серверный REST/WebSocket клиент Capital.com, библиотека `ws`, PostgreSQL через `pg`, свечной график Lightweight Charts. По package-lock: Next 16.4.2, React 19.3.0, pg 8.23.1, ws 8.21.3, TypeScript 5.9.3. Для worker/SQLite предусмотрен Node 24.

Vercel обслуживает HTTP. Подключён отдельный Neon PostgreSQL, ресурс `capital-live-archive`, план Free. SQLite — только локальная/self-hosted альтернатива, на Vercel запрещена кодом. Таблицы: `capital_ticks`, `capital_edges`, `capital_worker`.

Поток данных: Capital REST/WebSocket → валидация → JSON API и архив. `quote-at` сначала ищет точное совпадение provider timestamp в архиве, затем запрашивает историческую минутную свечу Capital.com. MN1 строится из дневных OHLC. Ни сделок, ни изменений торгового счёта для этого не требуется; среди просмотренных API-маршрутов endpoints размещения ордеров не обнаружены.

В репозитории нет исходного генератора макро-EDGE из ChatGPT. Проверка сохранности внешних торговых правил/алертов за пределами этого проекта не выполнена и не может быть выведена из успешных тестов market-data API.

**4. Контракт API: что именно проверять**

GET `/api/quotes`

Сохранены `markets`, `quotes`, `server_time`, `serverTime`, `fetchedAt` и 13 исходных публичных символов. `markets` и `quotes` должны совпадать. Макро-контекст возвращается отдельно.

Для цены проверять `bid <= ask`, конечные числа, `source_type`, `provider_timestamp`, `received_at_utc`, `fetched_at_utc`, `environment`, `market_status`, `age_seconds`. Возраст вычисляется как `(fetched_at_utc - provider_timestamp) / 1000`. Если provider timestamp неизвестен, возраст должен быть `null`, а не нулём или возрастом HTTP-запроса. REST timestamp нельзя брать из другого ответа и прикреплять к цене текущего snapshot. `quote_time` — совместимый алиас provider времени.

Диагностика: `diagnostics.websocket.request.instruments[epic]` содержит подтверждение подписки, последний фактический тик и fallback reason. Сама подписка ещё не доказывает получение тика. Короткое окно HTTP-сбора — 2500 мс; отсутствие тика в нём может дать REST fallback даже при исправном WebSocket. Нельзя требовать `WEBSOCKET` в каждом отдельном запросе. Не следует скрывать такой результат или называть REST свежим без timestamp.

`archive_status: ready` означает доступность операций архива, а не непрерывность покрытия. Для worker нужны его реальное состояние и свежий heartbeat. Текущий `worker: null` — незавершённый запуск, не успех 24/7. HTTP 200 или health `ready` также не доказывают свежие тики всех инструментов.

GET `/api/candles?symbol=BRENT&timeframe=MN1&limit=60`

MN1 принимает 1–60. W1/D1/H4 — 1–1000. Без параметра timeframe по совместимости используется H4; явно переданный пустой или неизвестный интервал должен вернуть HTTP 400. Поддерживаются MN1/W1/D1/H4, регистр нормализуется.

MN1 собирается из DAY по календарю UTC. Open — первый доступный дневной Open; High/Low — экстремумы; Close — последний доступный дневной Close. Bid/Ask независимы. WEEK не используется. `start_time` включительно, `end_time` — исключительная граница следующего месяца. Текущий месяц должен иметь `is_closed: false` по состоянию на `fetched_at`.

Проверять `source`, `first_daily_bar`, `last_daily_bar`, `daily_bars`, `history_completeness`, rejected counters и aggregation metadata. 60 возвращённых месяцев НЕ доказывают наличие всех торговых сессий. Без проверенного биржевого календаря полнота остаётся неизвестной. Отклонённые/неполные дневные данные помечают месяц как `partial_validation`. Отсутствующая сторона дневной свечи делает соответствующую месячную сторону null; её нельзя копировать с другой стороны.

GET `/api/structure?symbol=BRENT&mn1=60&w1=52&d1=180&h4=120`

Ожидаются массивы MN1/W1/D1/H4 и соответствующие metadata. ВАЖНО: MN1 включается явным `mn1`; отсутствие MN1 в старом запросе без `mn1` — выбранное поведение совместимости, не скрытая замена MN1 на H4. Если любой запрошенный timeframe недоступен, endpoint возвращает ошибку, а не успешную неполную структуру.

GET `/api/quote-at?symbol=BRENT&at=2026-11-05T21:21:30Z`

Ожидаемый подтверждённый ответ на дату аудита: `status: interval_estimate`, `exact: false`, `quote: null`, интервал `[21:21:00,21:22:00)` UTC, `source_type: CAPITAL_HISTORICAL_MINUTE`. OHLC этого интервала:

```json
{
  "open":  {"bid":97.928,"ask":97.968},
  "high":  {"bid":97.988,"ask":98.033},
  "low":   {"bid":97.903,"ask":97.958},
  "close": {"bid":97.981,"ask":98.026}
}
```

Close/High/Low могут включать события после 21:21:30. Нельзя использовать их как точную цену в момент сигнала или как информацию, уже известную на тот момент. Проверять `includes_prices_after_requested_at` и `is_exact_tick: false`.

GET `/api/quote-at?symbol=BRENT&at=2026-11-06T04:38:58.764Z`

Подтверждённый ответ: `exact_tick`, `exact: true`, Bid 99.004 / Ask 99.044, источник WEBSOCKET, provider timestamp совпадает с запросом. Этот тик получен сервером позже на 0.339 секунды — разница раскрыта. `exact_tick` означает сохранённое наблюдение с совпадающим временем провайдера; это НЕ утверждение, что сервер уже знал его в эту миллисекунду. Приём EDGE отдельно различает время провайдера и время получения.

Если точного совпадения и минутного интервала нет, ожидается `no_data`. `previous_observation` — отдельное более раннее наблюдение со смещением, не точная цена запрошенного момента. Сетевые/auth ошибки должны оставаться ошибками, а не превращаться в вымышленный `no_data` или текущую цену.

POST `/api/edge`

Код требует Bearer `EDGE_INGEST_TOKEN` и базу. При отсутствии конфигурации возвращается 503. Поля события: `id`, `symbol`, `original_time` в UTC, `direction`, числовой `edge`, `source`. Сохраняется исходное значение без пересчёта. Выбирается цена с provider временем не позже сигнала, по возможности также полученная не позже сигнала. Запись содержит age/deviation/quality. Повтор environment+source+id не должен переписывать результат; конфликт — 409. Ретроспективное заполнение старого no_data новым тиком запрещено.

Не отправлять вымышленные EDGE в production ради аудита. Тесты этого пути выполнять на тестовой БД с разрешённым токеном. Токены, пароли и DATABASE_URL не запрашивать и не печатать в ответе GPT.

**6. Как выполнить независимую проверку без секретов**

Публичные ссылки:

```text
https://capitalive.vercel.app/api/quotes
https://capitalive.vercel.app/api/markets
https://capitalive.vercel.app/api/health
https://capitalive.vercel.app/api/candles?symbol=BRENT&timeframe=MN1&limit=60
https://capitalive.vercel.app/api/structure?symbol=BRENT&mn1=60&w1=52&d1=180&h4=120
https://capitalive.vercel.app/api/candles?symbol=BRENT&timeframe=UNKNOWN
https://capitalive.vercel.app/api/candles?symbol=BRENT&timeframe=
https://capitalive.vercel.app/api/quote-at?symbol=BRENT&at=2026-11-05T21:21:30Z
https://capitalive.vercel.app/api/quote-at?symbol=BRENT&at=2026-11-06T04:38:58.764Z
```

Для всех семи MN1 повторить candles запрос со сменой symbol. Сверять декабрь/январь и текущий месяц. Для независимого пересчёта закрытых месяцев BRENT/NAS100 можно использовать `/api/candles?symbol=BRENT&timeframe=D1&limit=1000` и аналогичный NAS100: брать только месяцы, целиком попадающие в окно D1, сортировать по UTC, агрегировать каждую сторону отдельно. Сравнение незакрытого месяца при разных fetched_at может законно расходиться из-за новых цен.

Сохранять HTTP status, Content-Type, время запроса, raw JSON, source/environment и diagnostics. Соблюдать `Retry-After` на 429. Не запускать нагрузочный тест production. Недоступность URL в инструменте GPT, его кэш или ограничение браузера не следует выдавать за доказанный HTTP-ответ сервера.

В распакованном исходном проекте с Node 24:

```sh
npm ci
npm test
npm run lint
npm run build
npm audit --json
npm run test:release -- https://capitalive.vercel.app
node scripts/verify-recorded-data.mjs
```

`test:release` сохраняет реальные ответы в verification. `api_checks_passed: true` и `all_requested_capabilities_verified: false` совместимы: HTTP-функции исправны, но worker не работает. Не стирать это различие. `verify-recorded-data` пересчитывает ранее скачанные provider данные, а не делает новый live запрос. Unit-тесты используют фикстуры и не доказывают наличие настоящих тиков.

Архивный lookup можно проверить без DB-секрета: получить `/api/quotes`, взять реальный `provider_timestamp`, затем вызвать `/api/quote-at` с ним. Если BRENT пришёл по REST без timestamp, допустимы несколько ограниченных повторов; придумывать timestamp нельзя. Для 24/7 нужна отдельная длительная проверка heartbeat/получения/записи без HTTP-опроса quotes, включая рестарт worker и разрыв сети. Она ещё не проведена.

**7. Задание проверяющему GPT**

Проведи независимый аудит по приложенным исходникам, manifest, логам и настоящим HTTP-ответам. Не принимай этот документ и README за доказательство без проверки. Не меняй код, не развёртывай сервисы, не отправляй EDGE, не подключай платные планы. Бюджет владельца — только бесплатные варианты.

Ответ представь как таблицу: требование → способ проверки → фактический результат → статус PASS/FAIL/NOT VERIFIED → доказательство (URL, HTTP status, JSON-путь или файл:строка). Отдельно перечисли найденные дефекты с воспроизводимым примером, приоритетом и минимальным предлагаемым исправлением.

Обязательные вопросы: отличается ли provider time от времени получения; не подменяется ли неизвестный timeframe; правильно ли собраны MN1; есть ли look-ahead в использовании минутных OHLC; что именно означает exact_tick; работает ли БД вне функции; запущен ли worker; активирован ли приём EDGE; можно ли доказать неизменность исходного EDGE; ограничены ли нагрузка/квоты; воспроизводим ли релиз. Не называй готовым исследование «любого EDGE», если подтверждена только выборка сохранённых тиков.

В конце сформулируй, какие заявления можно делать сейчас, какие требуют оговорок и что конкретно осталось для непрерывного воспроизводимого архива. Если инструментов доступа к сети/исходникам нет, обозначь это как NOT VERIFIED, а не как успех или дефект сайта.
